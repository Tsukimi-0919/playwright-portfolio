# テスト戦略メモ（HOTEL PLANISPHERE）

> このファイルは「なぜこのテストを書いたか／書かなかったか」を残す場所です。
> コードより先に観点をここへ書き、そこからテストを起こします。

## 1. 目的

- 宿泊予約サイトの主要な利用シナリオが壊れていないことを、リグレッションとして自動で確認する
- 学習目的：Playwright での E2E テストの設計・実装・CI 運用を一通り経験する

## 2. 対象範囲

| 機能 | 自動化 | 理由 |
|---|---|---|
| ログイン | ✅ | 全機能の入口。登録済みユーザー4件でデータ駆動にしやすい |
| プラン一覧 → 予約画面 | ✅ | 新規ウィンドウが開く。E2E で確認する価値が高い |
| 予約フォームの入力切り替え | ✅ | 画面の動的な振る舞いで、手動だと確認漏れしやすい |
| 予約フォームの境界値 | 🔜 | 観点表を作成中（下記） |
| 合計金額の計算 | 🔜 | 期待値表を作ってから実装 |
| 会員登録 | ⏸ | Local Storage に保存される。まず主要シナリオを優先 |
| 見た目・レイアウト | ❌（手動） | 判断に人の目が必要。必要ならビジュアル比較を検討 |

## 3. テスト観点表（予約フォーム）

| 項目 | 同値クラス／境界 | 期待結果 | 自動化 |
|---|---|---|---|
| 宿泊数 | 下限-1 / 下限 / 上限 / 上限+1 | 範囲外はエラー表示 | 🔜 |
| 人数 | 下限-1 / 下限 / 上限 / 上限+1 | 範囲外はエラー表示 | 🔜 |
| 宿泊日 | 過去日 / 当日 / 3か月以内 / 3か月超 | 3か月超はエラー表示 | 🔜 |
| 確認のご連絡 | 希望しない / メール / 電話 | 対応する入力欄だけ表示 | ✅ |

※ 上限・下限はプランによって変わるため、プランごとに確認して埋める

## 4. 方針

- **ロケーター**：`getByRole` / `getByLabel` などユーザー視点のものを優先し、CSS セレクターは最終手段
- **構造**：Page Object Model（`pages/`）とテストデータ（`test-data/`）を分離
- **安定性**：固定の待ち時間（`waitForTimeout`）は使わず、自動待機とアサーションに任せる
- **練習サイトへの配慮**：負荷テストはしない。CI の並列数は控えめにする
