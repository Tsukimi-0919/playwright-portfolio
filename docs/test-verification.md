# テストの妥当性確認

> 「テストが通る」だけでは、テストが正しいとは言えない。
> **わざとバグを入れたときに、狙ったテストが失敗するか**を確かめた。

## 方法

1. HOTEL PLANISPHERE のソース（MIT License）を手元に取得し、ローカルで起動
2. 計算やチェックの処理を**1か所だけ**わざと壊す
3. 全テスト（75本）を実行し、**失敗したテストが観点表のどの番号か**を確認
4. 元に戻して、次の変更を試す

## 結果

| No | 入れたバグ | 失敗したテスト | 期待どおりか |
|---|---|---|---|
| M1 | 土日の25%割増しを無効にする | A-2, A-3, A-5, A-6, A-10, A-11, A-12（7本） | ✅ 土日を含むケースだけが失敗。平日だけのケースは通った |
| M2 | 朝食を泊数分にせず1回分にする | A-7, A-11, A-12（3本） | ✅ 朝食を含むケースだけが失敗 |
| M3 | 一般会員にもプレミアムプランを見せる | C-2（2アカウント）, C-5（3本） | ✅ 一覧の表示と URL 直接アクセスの両方で検知。プレミアム会員のテストは通った |
| M4 | 電話番号を10〜11桁まで許す | B-2-3 の10桁, エラー後の修正（2本） | ✅ 12桁など他の形式のテストは通った |
| M5 | 確認画面の合計だけ1,000円ずらす | A-12（1本） | ✅ 予約画面の金額テストは通り、確認画面との一致テストだけが検知 |

5つのバグすべてを検知でき、**関係のないテストは失敗しなかった**。

## わかったこと

- **A-12（確認画面との一致）は M5 を検知できる唯一のテスト**。予約画面の金額だけを見ていたら、確認画面のバグは見逃していた
- **A-11（全部の組み合わせ）は M1・M2 のどちらでも失敗した**が、それだけでは原因が分からない。A-7（朝食だけ）や A-2（土曜だけ）が一緒に失敗することで、**どのルールが壊れたか絞り込める**
- **C-5（URL 直接アクセス）は M3 を一覧とは別の角度から検知した**。「表示されない」と「利用できない」を分けて確かめた意味があった

## そのほかの確認

| 確認 | 方法 |
|---|---|
| 観点表との対応 | `npx playwright test --list` のテスト名と観点表の番号を突き合わせ、抜け・重複がないことを確認 |
| 実行日への依存 | 宿泊日を曜日で指定しているため、どの曜日に実行しても同じ結果になる（CI で毎回確認） |
